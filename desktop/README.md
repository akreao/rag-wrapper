# Desktop app

A Tauri app that runs the server: it drives `docker compose` on the stack in this repository. It has no account features beyond creating the first admin; players use the web portal.

What it does:
- **First run** asks for an admin username and password and the address players connect to, then writes `.env`: the admin as `ADMIN_USER`/`ADMIN_PASSWORD`, `PUBLIC_IP`, and random `DB_PASSWORD`, `DB_ROOT_PASSWORD` and `INTER_PASSWORD`. `db-init` creates the admin as a GM on the next start, after which the app blanks `ADMIN_PASSWORD` so no plain-text copy stays on disk.
- **Start** runs `docker compose up --detach`. When the rAthena or portal image is missing, it first downloads the prebuilt one for these settings (see [Prebuilt images](#prebuilt-images)); one that isn't published is built by `up`. The build's output streams into the Activity pane with a step counter.
- **Stop** runs `docker compose down`. The database volume is kept.
- **Rebuild** downloads the prebuilt images for the current settings and builds any that aren't published with `docker compose build`.
- **Rebuild needed** or **Rebuild recommended** shows above every screen when an image here is out of date and Start can't download a newer one: the game server was built for other build settings than the saved ones (needed), or this app version changed the build files and nothing ready-made could be downloaded (recommended). `images.json` in the stack folder records what each pulled or built image was made from. After a Rebuild that changed only the portal, the restart bar offers **Restart the portal**, which keeps players connected.
- **Server update available** shows above every screen when this version of the app comes with a different rAthena commit (`RATHENA_REPO` and `RATHENA_COMMIT` in the bundled `.env.example`) from the one in the user's `.env`, with a link to GitHub's list of the commits in between. Nothing changes until **Update server** is clicked. It backs up the database ("Before a server update"), downloads or builds the images at the new commit (a build gets it through `docker compose build`'s environment, so `.env` still names the old one), and only once that has succeeded writes the new commit into `.env`. A running server keeps going on the old image: a **Restart on the new version** bar shows whenever the map server's image isn't the one now built (after an update or a Rebuild), and clicking it runs `docker compose up --detach`, so `db-init` applies the new commit's database upgrades before the game servers restart. Settings' **Restart game servers** does the same full `up` in that state. A stopped server picks it up at its next Start. A failed or cancelled build leaves the old image running, `.env` untouched and the update on offer. **Not this one** keeps the current commit. Either way `.env` records the offered commit as `RATHENA_COMMIT_OFFERED`, so it isn't offered again, and a commit set by hand later (to test a fork change) isn't offered back; the next app version's commit is.
- **Settings** (the header button) has two parts:
  - **Game settings**: the server name shown in the client, the message of the day, and whether players get rAthena's "Super Player" helper commands (@autoloot, @go, @rates, @whodrops and the rest). Saving writes rAthena overrides into the stack's `overrides/` folder (see below); they apply when the game servers next start, and the screen offers **Restart game servers**, which recreates the login, char and map containers while the database and portal keep running. Values left at their defaults are left out of the files, so rAthena's stock config applies. **Open override folder** opens it for everything else.
  - **Battle config…** opens the battle config editor in a window of its own: every option in rAthena's `conf/battle/*.conf` files (exp and drop rates and the exp lost on death included), one file at a time from a list, or searched across all of them, each with the comment above it in the file, its value and its default. Changed options are highlighted, with a **Reset** back to the default. The files are copied out of the rAthena image (`docker create` and `docker cp`) into `.battle-conf/` in the stack directory the first time the editor opens after a build or pull, so they always match the server that runs; before the first build the editor says to start the server once. Saving checks each value the way rAthena reads it (yes/no or a whole number, hex allowed; one character for the command symbols) and writes only the changed options into `overrides/battle_conf.txt`; a value set back to its default is removed from the file. The default for `charcommand_symbol` is the stack's `*`. rAthena's allowed range for each number isn't in the image, so while the map server runs the editor reads its log since the last start for `Value for setting ... is invalid (min max)` warnings and marks each option the server turned down (while it still has that value) with its range and the value used instead, and the file list shows ⚠ on its file. While the server runs, a saved change offers **Restart game servers**, which runs in the main window. Closing the window with unsaved changes asks first.
  - **Server build**: the client date (`PACKETVER`, with 20250716, the default, and 20220406 as presets or any other date) and Pre-renewal (the default) or Renewal (`PRERE`). A change shows a warning, and saving it rebuilds the images and, if the server was running, starts it again on the new build.
- **Services** shows each service's state and published ports, refreshed every 3 seconds. Clicking one streams its logs.
- **Dashboard** (the header button opens its own page) lists the characters in game (name, class, base and job level, map) from the `char` table's `online` flag in the game mode's characters database, read with the database's own `ragnarok` account in the `db` container, with the player count and how long the map server has been up. Below it, each running container's CPU (as a share of the whole computer) and memory from `docker stats`, with a total. It refreshes every 5 seconds while the page is open and the window isn't minimised. The list is empty while the char server is down, since the flags are only kept current while it runs.
- **Address players connect to** defaults to *Detect automatically*: on every Start the app writes the machine's current LAN IP (the interface with the default route, skipping Docker's bridges and VPNs) as `PUBLIC_IP`. The list also offers the other LAN addresses, any VPN address (Tailscale's `tailscale0`, ZeroTier's `zt*`, WireGuard's `wg*` and NetBird's `wt*` interfaces, and any other 100.64.0.0/10 address as Tailscale), `127.0.0.1`, and *Type an address…* for any other IPv4 address. Picking one pins it (`PUBLIC_IP_AUTO=no` in `.env`). The app doesn't install or manage the VPN. A note under the list explains the catch: rAthena sends every player the same char and map address, so with a VPN address chosen, players at home must join the VPN too, and with a LAN address, friends on the VPN can't connect. Changing the address while the server runs asks first, then recreates the `char`, `map` and `portal` containers (the portal's "How to connect" page shows the address); the login server and database keep running. If a Rebuild or update is waiting, it does the full `up` instead, as Restart does.
- **Account portal port** sets `PORTAL_PORT` (8080 unless changed), for when another program on the computer already uses 8080. Changing it while the server runs recreates only the `portal` container. Before every start the app checks the ports the stack publishes; when one is taken it stops before `docker compose up` and says what holds it: another Docker container by name, or another program, with the `ss` command that names it.
- While the `portal` service runs, a link opens the account portal.
- **Backups** (the header button opens its own screen) keeps gzipped dumps of the `ragnarok` databases (accounts, and each game mode's characters) in `~/.local/share/app.ragwrapper.desktop/backups/` (`backups/` in the stack directory when `RAG_WRAPPER_STACK_DIR` is set). **Back up now** makes one; **Rebuild**, **Update server** and saving a build setting make one before the build, since the new build may upgrade the database on its next start. **Stop** and closing the app make one too, when there's no backup of any kind from the last 24 hours and the database is running. The newest 10 made with Back up now are kept, and separately the newest 10 made automatically, so rebuilds never push out a backup made by hand. A backup is `mariadb-dump --lock-all-tables` run in the `db` container (most of rAthena's tables are MyISAM, so a transaction alone wouldn't give a consistent copy; writes pause for the seconds it takes). It first repairs any table an unclean shutdown left marked as crashed, which MariaDB can't do under the dump's lock. If the server is stopped, the app starts the database for the backup and stops it again. Each file is named `ragnarok-YYYYMMDD-HHMMSS-<reason>.sql.gz`.
- **Client patch** (the header button opens its own screen) publishes files to the players' patcher, which they download from the portal's How to connect page. The files go in `~/.local/share/app.ragwrapper.desktop/client-files/` (`client-files/` in the stack directory when `RAG_WRAPPER_STACK_DIR` is set), laid out like the game client's folder: the patched client as `rag-wrapper.exe`, GRF content under `data/`, and anything else (such as `System/` files) where it goes in the client. The screen lists what changed since the last patch; **Publish client patch** builds THOR patches of just those files into the stack's `patches/` folder and adds them to `plist.txt`, and the portal serves them at once. Files under `data/` go into `rag-wrapper.grf`, and from then on every patch also writes the client's `DATA.INI` (`rag-wrapper.grf` above `data.grf`). Files deleted from the folder are deleted from the players' clients too. Publishing waits while a file can't be handed out as it is: no `rag-wrapper.exe`, another `.exe`, a `.grf` or `DATA.INI` of its own, or a name the client can't read. Names outside `data/` must be ASCII; Korean names under `data/` are written in the client's code page, whether they're spelled in Hangul or in the Latin letters a GRF tool on Windows shows. `patches/published.json` records each published file's checksum and the history the screen shows. Enabled mods' `client/` folders are added after it, in load order, with Lua tables merged entry by entry; the screen names those mods and lists anything two of them set differently.
- **Mods** (the header button opens its own screen) lists the folders in the stack's `mods/` folder, one per mod, with the NPC scripts and database files each one loads, a checkbox to switch it on or off, and arrows to change the load order of the ones that are on (the later one wins where two set the same value differently), all written to `mods/enabled.txt`; a mod switched on goes to the end. Changes apply when the game servers next start: while they run, a mod switched on or off, or one whose files changed, since they started is marked (a new order isn't marked per mod but also offers the restart), and the screen offers **Restart game servers**. When that restart (or a Start) brings in a mod's database files for the first time, the database is backed up first (edits to ones already loaded don't trigger another) ("Before loading a mod's database files"). Errors and warnings in the map server's log that name a mod's file show under that mod, a script error with the code around it. Clashes, values two mods set differently, show under both mods as soon as they change: whenever the enabled mods, their order or their database files change, the app runs `merge_mods.py --check` in the rAthena image (`docker run`, no network, the mods folder read-only) and shows its `Mod clash` lines; with an image that predates the check, it uses the ones the map server logged at its latest start. The screen refreshes every 5 seconds while it's open. `mods/.applied.json` records the mods the last Start or restart from the app loaded. When mods are on but the running map server's log lacks the `Mods enabled:` line the entrypoint prints, the image was built before mod loading, and the screen asks for a Rebuild instead. **Open mods folder** opens it to copy mods in. See [`mods/README.md`](../mods/README.md) for a mod's layout. A mod's `client/` files go out with the next client patch instead of loading on restart, and clashes in them show under each mod too.
- **News** (the header button opens its own screen) edits the account portal's news, `overrides/portal/news.md`: one card per post, newest at the top, each a title and Markdown text, plus a folded "Top of the News page" box for anything above the posts, such as the rules. **New post** adds one on top whose text starts with today's date, **Delete** drops one, and **Save** writes the whole file in the portal's layout (a `## ` heading per post) and removes it when nothing is left. The portal reads the file on every request, so a save shows on the News page and in the patcher's window straight away. Save refuses when the file was edited by hand since the screen loaded it, so that edit isn't lost (**Reload** shows it), and when a post's text has a `## ` line of its own, which would split it in two.
- **Restore** on a backup asks for confirmation, checks the file is a whole dump, stops every service but the database, backs up the current database ("Before a restore"), drops the `ragnarok` databases, loads the dump, and starts the server again if it was running. `db-init` then applies any upgrade files the backup predates. **Open folder** opens the backups folder so files can be copied elsewhere; a file copied back in with the same naming shows up in the list.
- **Test** on a backup proves it would restore without touching the live database. It checks the file is a whole dump, starts a throwaway container of the stack's MariaDB image (`rag-wrapper-restore-test`, no network, no named volume), loads the dump into it the way Restore does, and checks that every database the dump creates is there, that `mariadb-check` finds every table OK, and how many accounts, characters and inventory items it holds. The Activity log shows those counts next to the live database's when it's running. The container and its data are removed afterwards. The result shows under the backup's row ("Tested 2026-10-15 12:30: loads, 12 accounts, 40 characters", or what went wrong) and is kept in `.restore-tests.json` in the backups folder. Restore on a backup whose last test failed says so in its confirmation. Closing the app cancels a test.

### Prebuilt images

CI publishes the rAthena image for each pinned commit, in both modes for the two PACKETVER presets, and the portal image, to `ghcr.io/akreao/` (`.github/workflows/images.yml`). The app pulls the one matching the server's settings and tags it with the name Compose uses (`rag-wrapper/rathena:<PACKETVER>`, `rag-wrapper/portal`), so the first start and a server update take a download instead of a 5 to 10 minute compile. A tag names everything the image was built from: `rag-wrapper-rathena:<PACKETVER>-<prere|re>-<commit>-<hash>` and `rag-wrapper-portal:<hash>`, where the hash covers the files in `docker/rathena/` or `portal/` that came with the app, so an app version with a changed entrypoint or portal never gets an old image. Anything not published (another PACKETVER, a hand-set commit, a different `RATHENA_REPO`, no network) falls back to building here. `PREBUILT_IMAGES=` (empty) in `.env` always builds here.

The server runs only while the app is open: closing the window cancels any build or start in progress, runs `docker compose down` (keeping the database volume) and then exits.

## Where the stack lives

The app bundles `compose.yaml`, `docker/`, `portal/` and `.env.example`, and copies them to `~/.local/share/app.ragwrapper.desktop/stack/` on every launch, so app updates bring stack updates. `.env` there is the user's and is never overwritten. The Compose project is always named `rag-wrapper`, so containers and the `rag-wrapper_db-data` volume keep their names.

To point the app at another stack directory, such as this checkout while developing, set `RAG_WRAPPER_STACK_DIR`:

```sh
RAG_WRAPPER_STACK_DIR=$PWD/.. cargo run
```

## Overrides

`overrides/` in the stack directory is mounted into every rAthena container as `conf/user/`. On start, `entrypoint.sh` uses each file there that is named like one of rAthena's `conf/import/` files (`battle_conf.txt`, `char_conf.txt`, `map_conf.txt`, `groups.yml`, ...) in its place, before the stack's own values, so the database, addresses and server passwords can't be overridden by mistake. The Settings screen edits only its own lines in those files; see [`overrides/README.md`](../overrides/README.md).

## Mods

`mods/` in the stack directory is mounted, read-only, into every rAthena container as `mods/`. On start, `entrypoint.sh` loads the mods named in `mods/enabled.txt`, in that file's order: each mod's `npc/**/*.txt` through an `npc/mods.conf` that `npc/scripts_custom.conf` imports, so they load after rAthena's own scripts and survive `@reloadscript`, and its `db/*.yml` (plus `db/pre-re/` or `db/re/` for the game mode) as `Footer` imports of the matching `db/import/` file, which it resets from `db/import-tmpl/` first. Database files with any other name are skipped with a warning in the log.

Before that, `merge_mods.py` reads the enabled mods' database files: it logs a `Mod clash` warning wherever two mods set the same value differently, and writes `db/import/mods-merged/` files, loaded after the mods, for fields rAthena resets on each import (an item's `Jobs`), so those combine too. Where more than one mod adds the same monster drop, it loads the earlier mods' files from copies under `db/import/mods-merged/mods/<name>/` with that drop commented out, keeping the lines in place; the Mods screen counts errors in those copies under the mod. Its table of how each rAthena database keys its entries and lists (`RULES`) comes from rAthena's loaders; `test_merge_mods.py` next to it holds the tests.

## Building

Needs Rust, the Tauri prerequisites for Linux and Docker with the Compose plugin; the user running the app must be in the `docker` group.

```sh
# Ubuntu 24.04
sudo apt install libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev libssl-dev build-essential file
cargo install tauri-cli --version "^2" --locked

cd desktop/src-tauri
cargo run                          # development build
cargo test                         # unit tests
cargo tauri build                  # the AppImage, in target/release/bundle/appimage/
```

## Releasing

Releases are AppImages built by GitHub Actions ([`release.yml`](../.github/workflows/release.yml)) on Ubuntu 22.04, so they run on distributions with an older glibc than the newest Ubuntu. To release, raise the version in `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` (they must match) and add the release notes as `docs/releases/<version>.md`, in one PR. When it merges, the workflow sees that `main`'s version has no release yet, builds `rag-wrapper-<version>-x86_64.AppImage` and publishes it as release `v<version>`, creating the tag itself. Nobody pushes tags. Pushes to `main` that leave the version alone build nothing.

Pull requests that change the packaging or the release notes build the AppImage too and keep it as a workflow artifact for 14 days; **Run workflow** on the Release workflow does the same for any branch.

Inside the AppImage, its launcher points `LD_LIBRARY_PATH`, `XDG_DATA_DIRS` and GTK's module paths at the libraries bundled with it. The app takes those entries out again for every program it starts (`docker`, and `xdg-open` for folders and web pages, in `src/host.rs`), so the host's own file manager and browser don't load the bundled libraries.

Run from the AppImage, the app also writes an applications menu entry on every launch (`src/menu.rs`), pointing at the AppImage's current path.

The UI is plain HTML, CSS and JavaScript in `ui/`; there is no npm step.
