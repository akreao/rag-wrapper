# Mods folder

Roadmap feature 6, custom content: a server-side mods folder that the desktop app switches mods on and off in. PR #17.

- **The mods folder sits in the stack, beside `overrides/` and `patches/`**: `~/.local/share/app.ragwrapper.desktop/stack/mods/`, mounted read-only into every rAthena container as `/rathena/mods`. Like the overrides it's kept across app updates, and people running the stack without the app use the same folder.
- **One folder per mod, with `npc/` and `db/` inside.** Every `.txt` file under `npc/` is a script. `db/*.yml` files are named like rAthena's `db/import/` files (`item_db.yml`, `mob_db.yml`, ...) and written in the same format; `db/pre-re/` and `db/re/` hold files for one game mode only. Folder names are limited to letters, digits, `.`, `_` and `-`, since they end up in config and YAML files.
- **`mods/enabled.txt` says which mods are on**, one name per line. The Mods screen rewrites it; people without the app edit it by hand.
- **Mods load in the order of `enabled.txt`, and the later one wins.** When two mods change the same database entry, rAthena applies both in order, so the later mod's fields win. The Mods screen lists the mods that are on in that order, with arrows to move each one up or down; a mod switched on goes to the end. This settles the roadmap's open load-order question (see the review answer below).
- **Scripts load after rAthena's own, through `npc/scripts_custom.conf`.** The entrypoint writes `npc/mods.conf` and adds one import line for it to `npc/scripts_custom.conf` in the container. Listing the scripts in `map_conf.txt` instead would load them before rAthena's scripts and lose them on `@reloadscript`.
- **Database files load as `Footer` imports of the `db/import/` files.** On every start the entrypoint copies rAthena's `db/import-tmpl/*.yml` back over `db/import/` and appends the enabled mods' files as imports, so a mod switched off leaves nothing behind. rAthena reads them after its own entries and `db/import`. A file in `db/` with any other name is skipped with a warning in the log.
- **Errors show under the mod, from the map server's log.** The screen picks out rAthena's `[Error]` and `[Warning]` messages that name a file under `mods/<name>/`, with a script error's code excerpt and a database error's file and line. This settles the roadmap's open question on how errors are shown.
- **Changes wait for a restart, and the screen says which.** After each Start or restart from the app, `mods/.applied.json` records the enabled mods and a checksum of their files' names, sizes and times. While the game servers run, a mod switched on or off, or with changed files, since then is marked "loads on restart" or "unloads on restart", and the screen offers **Restart game servers**.
- **The database is backed up before a mod's database files first load**, as the roadmap asked: when a Start or restart brings in an enabled mod whose `db/` files haven't loaded before (a mod just switched on, or one that gained its first database file), it makes an automatic backup ("Before loading a mod's database files") first. Scripts alone, and edits to database files that already loaded, don't trigger one (see the review answer below).
- **The portal's item names include mod items.** `db-init` adds the enabled mods' `item_db.yml` to the item names it loads, on the next full Start.
- **Existing installs need a Rebuild before mods load.** The entrypoint is part of the rAthena image, so an image built before this change ignores `mods/`. New installs build it with the image. The Mods screen warns when this happens (see the review answer below).
- **Checked against a real rAthena build** (the fork's `rag-wrapper` branch, pre-renewal, 20250716): an enabled mod's NPC loaded, its `item_db.yml` added an item and renamed Red Potion (in the map server and in the portal's item names), its `pre-re/mob_db.yml` loaded, and a broken mod's script and database errors were picked out of the map server's log under that mod.
- **No fork change.** Everything is in the stack's entrypoint; rAthena's own YAML imports and script imports do the loading.

Questions asked about the finished feature (PR #17), one at a time.

- **The mods folder stays in the stack folder**, `~/.local/share/app.ragwrapper.desktop/stack/mods/`, beside `overrides/` and `patches/`, rather than in the app's data folder beside `client-files/`. Compose mounts it with a relative path, and the stack run without the app uses the same folder.
- **The load order is set with arrows on the Mods screen**, not by folder names. The first build loaded mods alphabetically and had people rename folders (`10-`, `20-`) to reorder; now `enabled.txt` keeps the order and the screen's up and down arrows change it. A new order waits for a restart like any other change.
- **The Mods screen warns when the server needs a Rebuild to load mods.** The new entrypoint prints `Mods enabled: ...` on every start; when mods are on, the map server is running and its log has no such line, the image predates mod loading, so the screen says so and offers **Rebuild** (which backs up first, and is then followed by the usual "Restart on the new version" bar) in place of the restart notice.
- **A mod's database files trigger a backup only the first time they load**, not on every edit. Restarting to test changes to a custom item would otherwise make a backup each time, and with only the newest 10 automatic backups kept, push out the ones from before a rebuild or update.

## Merging mods' database changes

Roadmap feature 11, a follow-up to the mods folder. The roadmap asked for list fields such as a monster's `Drops` to combine across mods, the later mod to win where two set the same value, and each clash to be listed under both mods.

- **rAthena already combines almost every list, so the mods' files still load as they are.** Reading each database's loader in the pinned rAthena showed that an import changes only what it names: `Drops` without an `Index` are added to the monster's drops (up to 10, 3 for `MvpDrops`), keyed lists (skill tree skills, item group sub-groups, quest targets, cash shop items...) change only the keys they name, and maps of flags (`Jobs`, `Flags`, `Modes`...) only the flags they name. So there's no pre-merged file of everything: each mod's file keeps loading under its own path, which keeps rAthena's errors pointing at the right mod. The roadmap's guess that a later mod's `Drops` replace the earlier one's was wrong.
- **An item's `Jobs` is the one list that loses a mod's changes**, because rAthena resets the item's jobs to the ones an import lists. Where more than one mod sets `Jobs` on the same item, `merge_mods.py` writes the jobs they list together into `db/import/mods-merged/item_db.yml`, loaded after the mods, with a comment naming the mods. A mod's `Jobs` still replaces rAthena's own jobs for the item, as any import does.
- **A few other lists are replaced whole and count as one value**: `Probability` in `abra_db.yml`, `Random` and a slot's `Options` in `item_randomopt_group.yml`, and `Order` in `item_enchant.yml`. They're rare in mods, and combining two mods' copies has no clear meaning, so two mods setting one differently is a clash.
- **A clash is two mods setting the same value differently** in the same entry: the same field, or the same sub-entry's field (the same `Drops` `Index`, the same job). The same value from both isn't a clash, nor are two files from one mod. The later mod in `enabled.txt` wins, as before, except in `const.yml`, where rAthena keeps a constant's first value and the message says so.
- **Clashes are logged and shown under both mods.** `merge_mods.py` runs from `entrypoint.sh` on every start and prints a `[Warning]: Mod clash in <file>, <entry>, <field>: ...` line naming both files with their line numbers and values, and which mod's value is used. The Mods screen shows them in their own section under each mod named, apart from errors, as soon as the mods change (see the review answer below). Clashes never stop a start, and a failure in the script only logs a warning.
- **A drop that more than one mod adds is kept once**, from the mod latest in the load order (see the review answer below). Earlier mods' copies of it are left out: `merge_mods.py` loads those mods' files from copies in `db/import/mods-merged/mods/<name>/` with that drop commented out, line for line, so rAthena's errors still give the right line, and the Mods screen still files them under the mod. A different `Rate` or other setting for the same item is a clash. Drops one mod lists twice, or set by `Index`, are left alone.
- **`Header: Clear: true` in a mod's file gets a warning**, since it empties the database, rAthena's own entries and earlier mods' included.
- **The image gains Python and PyYAML** for `merge_mods.py`; the rules for each database are a table in it, taken from rAthena's loaders. Like any change to the image, it reaches existing installs with the app update that carries it (the image's tag includes a hash of `docker/rathena/`); until the new image runs, mods load as before, without the clash list.
- **Checked against a real rAthena build** (pinned commit, pre-renewal, 20250716): two mods each adding a drop to Poring gave it both drops, a clash on Poring's `Hp` and Red Potion's `Buy` used the later mod's value and was logged with both files, and the combined `Jobs` file loaded.

Questions asked about the finished feature (PR #24), one at a time.

- **Two mods adding the same drop to a monster give it once, not twice.** rAthena rolls every drop on its own, so a second copy doesn't dilute the others, but it doubles the item's chance and takes a second of the monster's 10 drop slots, which neither mod meant. Built in the follow-up PR.
- **Clashes show on the Mods screen as soon as a mod's files change**, not only after a restart. The app runs the server's own check (`merge_mods.py --check`) in the rAthena image whenever the enabled mods, their order or their database files change, so the rules stay in one place, and the screen refreshes every 5 seconds while it's open. When the image predates the check, it falls back to the clashes in the map server's log from its latest start.
- **A mod file with `Header: Clear: true` still loads, with a warning** under the mod. It empties that database, rAthena's own entries and earlier mods' included, which is how a mod replaces a whole table (custom EXP levels, say); skipping the file would guard against a copy-paste slip but rule that out.

## Barters and replacing NPCs

Asked when Steven tested his first mod (2026-10-15).

- **A mod's `db/barters.yml` loads**, under the `Footer` of `npc/custom/barters.yml`, since rAthena reads barters from `npc/barters.yml` rather than `db/import/`. The entrypoint keeps a copy of `npc/custom/barters.yml` from the first start and restores it on every start, as it does for the `db/import/` files, so a mod switched off leaves nothing behind. Clashes are checked like the other databases (by `Name`, then item `Index`). Before this the file was skipped with a warning.
- **Replacing one of rAthena's NPCs is done in the mod's script with `unloadnpc`**, not by the loader: an NPC with the same unique name loads as a second NPC and gets renamed, so the mod gives its NPC its own name and unloads the original `OnInit`. Checked on a real build: the original was gone and the mod's NPC stood in its place.
