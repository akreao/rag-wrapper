# Signed client patches

Audit finding 14 (2026-10-16 audit): nothing proved that client patches and the new patcher's self-update came from the server, so anyone who could sit in the middle of the LAN or VPN (ARP spoofing at a LAN party, a hostile VPN peer) could hand every player a program of their own. Asked for by Steven on 2026-10-16, with the patcher's smaller audit items (link buttons, required integrity).

- **The portal signs, with a key from `.env`.** `PATCH_SIGNING_KEY` is a secret the desktop app makes once (40 random letters and digits, at setup, or on the first Start of an install from before signing) and compose hands to the portal. The portal turns it into an ed25519 key (`portal/signing.go`). The audit suggested the desktop app's Publish button sign each patch instead, keeping the key out of the containers. Signing in the portal was chosen because the patcher's self-update has to be signed too, and the patcher exe is built into the portal image, where the desktop app can't see it; it also keeps patches added to `patches/` by hand working. Both protect against the attacker the audit describes, someone in the middle of the network. Neither protects players from a compromised portal, which could already change the patcher download itself.
- **One signature over `info.json`.** The info the patcher starts with now also lists each patch in `plist.txt` with its size and SHA-256. The whole info is encoded once and signed (`signed` and `signature` beside the plain fields), with a fixed context string in front so the signature can't be reused for anything else. The patcher uses only the signed copy: its patch list, the checksums it checks each download against before applying it, the patcher exe's checksum for the self-update, and the links. The plain fields stay for patchers from before signing, which read them to update themselves to this one.
- **The key is trusted on first use.** The patcher download (`rag-wrapper-patcher.json`) carries the public key. A patcher set up before signing has none, so it takes the key from the first signed `info.json` it gets and adds it to its config. From then on it refuses unsigned info, a wrong signature, a different key, and a patch whose checksum doesn't match, and says why in its window instead of "Can't reach the server". That trusts the first download or first start, as the audit noted, and protects every later one.
- **Never change the key.** Every player's patcher would refuse updates until they download the patcher again, which is what the error tells them to do. `.env.example` says so. A server with no key signs nothing, and patchers that never saw a key work as before.
- **rpatchur is unchanged.** It reads `plist.txt` and the patches as before and can't check signatures; it stays the main download until ours is confirmed on a player's Windows PC ([own-patcher.md](own-patcher.md)).
- **Link buttons open only the portal's pages.** The account, How to connect and News buttons only open `http` or `https` links on the same address and port as the portal in the patcher's config; anything else (a program, a share, a `file:` link) leaves the button doing nothing.
- **`data.integrity` is required.** A patch without it, or with a file it doesn't list, is refused, so every file is CRC-checked and size-checked before applying, GRF entries included (they used to be copied into the GRF unchecked). The desktop app always lists every file. A patch made by hand with rpatchur's `mkpatch` needs `include_checksums: true`.
