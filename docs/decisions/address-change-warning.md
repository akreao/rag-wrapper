# Address change warning

When the desktop app tells the user that the server's address moved and players need the patcher again (roadmap feature 15, this PR).

- **Why players need telling.** The patcher zip from the How to connect page carries the address it was downloaded from: `data/clientinfo.xml` (log-in), `ExternalSettings_kr.lub` (the web server, see [web-server-address.md](web-server-address.md)) and `rpatchur.yml` (`plist_url`, `patch_url`). After a move the client can't log in and the patcher can't reach the server to fetch a fix, so the only way back is a new download from the new address.
- **The app remembers where players reached the last successful start** in `.env` as `LAST_ADDRESS` (`PUBLIC_IP:PORTAL_PORT`), written after every start, restart, address change or portal port change that succeeds. When the server starts on another one, the old address goes in `ADDRESS_CHANGED_FROM` and the bar shows.
- **What counts as a move.** Both ways an address changes are covered by the same check: automatic mode picking up a new LAN address on Start, and a change in the address picker (which restarts the char and map servers when the server runs, or applies on the next Start). The warning shows once the server really runs on the new address, not when the picker is changed, since nothing changes for players before that.
- **Installs from before this feature** don't have `LAST_ADDRESS`. Their first start only records the address and doesn't warn, because the app can't tell whether it moved.
- **Several moves before players are told** keep the first old address, the one players still have. Moving back to it hides the bar, since players' files work again.
- **The bar** sits above every screen, shown alongside the update, rebuild and restart bars rather than queued behind them, because it's about players and none of those fixes it. It reads "The server's address changed from A to B. Players need to download the patcher again from the How to connect page", with **Copy the link** (the connect page on the new address and the portal port) and **Players know**, which hides it until the next move. Unlike the Rebuild bar it can be dismissed, because once players are told nothing is left to do on the server, and only Steven knows when they have been (Steven, 2026-10-15).
- **The router hint** (reserve the address with a DHCP reservation) shows only in automatic mode, since a pinned address moves only when picked by hand.
- **Host names instead of the IP were not built.** Putting the PC's `name.local` in `clientinfo.xml` and the patcher's URLs would make a new LAN address need no new download, but it needs mDNS working on Steven's PC (Avahi) and on every player's Windows PC, and whether the 20250716 client and rpatchur resolve `.local` names hasn't been checked. A player on a VPN can't resolve the name at all. A DHCP reservation fixes the cause with no code, so the idea is dropped rather than put on the roadmap (Steven, 2026-10-15).
- **A portal port change warns too.** It doesn't stop players logging in, but `rpatchur.yml` names the port, so their patcher can't fetch patches until they download it again. The bar then shows the old and new `address:port`; when only the address moved it shows the addresses alone (Steven, 2026-10-15).
