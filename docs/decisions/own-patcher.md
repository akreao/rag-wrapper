# Our own patcher

Roadmap feature 17: a client patcher of our own, in Go, to replace [rpatchur](https://github.com/L1nkZ/rpatchur), which has had no activity since about 2021 and only builds with Rust 1.68 ([client-patcher.md](client-patcher.md)). Asked for by Steven on 2026-10-15.

- **It lives in the portal's module** (`portal/cmd/patcher`) and the portal image's existing Go stage cross-compiles it for Windows (`GOOS=windows`, `-H windowsgui`). [go-winres](https://github.com/tc-hib/go-winres) (pinned, run at build time, nothing committed) adds the manifest for Windows' current control style, the icon and the file details. Go's licence goes in the download as `licenses/go-LICENSE.txt`.
- **It does what we used rpatchur for, and nothing more.** It fetches `plist.txt`, downloads each `.thor` it hasn't applied, checks every file against the patch's `data.integrity` CRC32s before touching anything, and applies it: into `rag-wrapper.grf` (the patch's target GRF, never `data.grf`) or into the client folder, removals included. Only the "multiple files" THOR mode is read, the only one the desktop app writes. Play starts `rag-wrapper.exe`, Settings starts `opensetup.exe`, both through `ShellExecute`, so a client that asks for administrator rights gets Windows' prompt.
- **Same place in the patch list as rpatchur.** It keeps the last applied patch number in rpatchur's own cache file, `rag-wrapper-patcher.dat`, in rpatchur's format, so a player switching between the two patchers (either way) doesn't download everything again. As in rpatchur, a number that isn't in `plist.txt` means the list was started over, and every patch applies again.
- **GRF patching is in place and safe to interrupt.** New content and a new file table go after the end of the GRF and the header is rewritten last, so until then the old table is whole. Replaced content stays behind as dead space until it outweighs the live content (and is over 1 MB); then the GRF is rewritten through a temporary file. It writes GRF 0x200, the version rpatchur creates. Checked both ways with rpatchur's own GRF code (`gruf`): it reads the GRFs ours writes, and ours patches GRFs it wrote.
- **Client-folder files are swapped in whole** (written beside, then renamed), and patch paths can't leave the client folder or overwrite the patcher's own files. When Windows refuses because a file is open, the error says to close the game.
- **A window drawn without a browser engine.** (Since 2026-10-23 a tabbed Gio window in the portal's look; see [launcher.md](launcher.md). What follows is the first version.) rpatchur showed `/patcher/` in Internet Explorer's engine, which caused the first "stuck on Checking for updates" bug. Ours draws its window with user32 controls (no browser engine, no cgo), which also runs under Wine: server name, the newest news post as plain text, progress, Play, Try again, Settings, Exit, and buttons that open the account, How to connect and News pages in the browser. Checked under Wine 9: patching, Try again after the portal was down, self-update, and Play starting the client and closing the patcher.
- **It asks the portal what to show.** `/patcher/info.json` gives the server name, the newest news post (its heading and its Markdown as plain text), the links, `plist.txt`'s and the patches' addresses, and the patcher's own checksum. The download's config, `rag-wrapper-patcher.json`, holds the portal's address (with `PUBLIC_IP` for downloads made on the server itself, as before) and the key the portal signs `info.json` with ([signed-patches.md](signed-patches.md)).
- **It updates itself.** When the portal's `rag-wrapper-patcher.exe` has a different SHA-256 from the running one, it downloads it, checks the checksum, renames itself to `.old` (Windows allows renaming a running program), puts the new one in its place and starts it, which deletes the `.old`. The new one doesn't check again on that run, so a mismatch can't loop. A failed update leaves the old patcher patching as usual. So a fix to the patcher reaches players with a portal update, not a new download.
- **It checks it's in a client folder.** With no `data.grf` beside it, it asks before patching, so the server's files don't land in a Downloads folder.
- **rpatchur stays until ours is confirmed on a player's Windows PC.** Steven can only run the client under Wine, and his Windows VMs can run the patcher but not the client. The portal image still builds rpatchur, and the How to connect page keeps rpatchur's download as the main one, with ours beside it as "the new patcher" (`/connect/rag-wrapper-patcher-new.zip`). Its exe has the same name as rpatchur's, so trying it replaces rpatchur in the client folder, and going back is downloading rpatchur's zip again.

Questions asked about the finished patcher (PR #52), one at a time.

- **One player's Windows PC decides.** Once one player's Windows test passes, a follow-up PR makes ours the main download and drops rpatchur and its Rust build from the portal image. Waiting for weeks of use or keeping rpatchur for good were the alternatives; the self-update means later fixes reach players anyway.
- **The patcher has the desktop app's icon.** A copy of `desktop/src-tauri/icons/icon.png` sits in `portal/cmd/patcher/` (the portal image's build only sees `portal/`), so players see the same icon in the client folder and the taskbar.
- **The patcher updates itself without asking.** Patches can already replace the client exe, so a Yes/No box before a patcher update would protect nothing; the window just says "Updating the patcher..." and restarts.
- **"Path not found" under Wine (Steven, 2026-10-15).** The new patcher stopped at start with only "Path not found" in a box. The one bare error box at start came from resolving the patcher's own path with `filepath.EvalSymlinks`, which isn't needed: the client folder is wherever Windows started the patcher. It now uses that path as it is, and the box names the step if finding it ever fails. Not reproduced here (Wine 9 and 11, plain, symlinked and drive-letter paths all worked), so the cause is inferred.

Fixes from the 2026-10-16 audit (items 7 to 9).

- **A GRF that can't be shrunk doesn't fail the patch.** Compaction runs after the patch is committed to the GRF. If it fails (antivirus holding the file, no room for the temporary copy), the patch still counts as applied and its number is saved; the last line says the GRF couldn't be shrunk. Before, the patch applied again on every run and the GRF grew each time. Compaction tries again with the next patch into that GRF, not on every start: dead space only costs disk space.
- **Removing files from a GRF is one pass.** A removal marks the entry and the commit drops all marked entries at once, keeping the others in order. It used to rebuild the whole index per removed file, which took minutes for thousands of removals from a large GRF.
- **Files are streamed, never held whole in memory.** The integrity check inflates each file into the CRC32 as it reads; client-folder files inflate into the temporary file, which is synced to disk before the rename. Both check the size against the patch's, so a GRF entry with the wrong size is refused too. GRF entries are still copied compressed, as stored.
