# Going back to the previous server version

Roadmap feature 23: undoing a server update from the desktop app, without waiting for an app release. Follows [server-updates.md](server-updates.md).

- **A Server version card on Settings.** It names the rAthena commit the server runs and the one before it, with **Go back to <commit>**, which asks once before doing anything, and a link to GitHub's list of the commits going back undoes. Not a bar above every screen: going back is something you look for after a bad update, not something to be told about.
- **Going back is an update the other way.** The database is backed up first ("Before going back to the previous server version"), the older commit's images are downloaded or built here, and `.env` moves only once that worked, so a failed or cancelled build changes nothing. A running server stays on the newer version until the restart bar is clicked; a stopped one picks it up at its next Start. The restart bar now says "A new server build is ready" and **Restart on the new build**, since after going back the build isn't a newer version.
- **One step back, and back again.** The previous commit is the one the server ran before its last update or go-back (`RATHENA_COMMIT_PREVIOUS` and `RATHENA_REPO_PREVIOUS` in `.env`). Going back swaps the two, so the button then returns to the newer commit. There's no longer history: one step undoes a bad update, and anything older is a hand-set commit. Steven chose one step over a list of past releases (2026-10-16): older releases mostly have no published image, so they'd compile here.
- **Installs that haven't moved since use the previous release's commit.** `.env.example` names it in `RATHENA_COMMIT_PREVIOUS`, used when the server is on this release's commit and `.env` has no previous one recorded (everyone who updated before this existed). Whoever moves `RATHENA_COMMIT` in a PR sets `RATHENA_COMMIT_PREVIOUS` to the old value; a test checks it's a full commit and not the current one.
- **CI publishes the previous release's commit too.** The images workflow builds every PACKETVER preset and mode for both commits, so going back is a download, not a compile. Its job names gain "(previous release)" for the new ones; the existing names are unchanged.
- **Going back stops this app version's update being offered.** It records this version's commit as offered, so the "Server update available" bar doesn't immediately offer the version just left. Going forward is the same button.
- **A database the newer version upgraded doesn't run older code.** `db-init` checks both databases' `wrapper_sql_upgrades` for files dated after the image's newest upgrade file; if there are any, it stops with a message naming them and the game servers don't start. The database is left as it is: going forward again works at once, or the backup made before the update can be restored (losing what happened since). Older files missing from the image (upstream renaming one) don't count, so this can't block a normal update. The smoke tests check the refusal. Steven chose refusing over a warning or an automatic restore (2026-10-16): older code never runs on a database it doesn't know, and player progress is never thrown away without asking.
- **No rAthena change.** 266a587 to 15a8dc8 (the emotion and stylist PRs) has no database upgrade, so going back from the current pin works without a restore.
